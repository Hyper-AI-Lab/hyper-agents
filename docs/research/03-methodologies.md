# Methodologies converge on one loop, and the heaviest frameworks lack proof

By 2026 the three major vendors describe essentially the same five-part workflow: a short, pruned, always-loaded instruction file plus on-demand skills; explore, then plan, then implement, with planning gated by task size; a machine-checkable "done when" signal that the agent runs itself; review in a fresh context; and parallelism through git worktrees and background or cloud agents. Anthropic's best-practices page organizes everything around one constraint: "Claude's context window fills up fast, and performance degrades as it fills." Its first tip is verification: "Give Claude a check it can run... It's the difference between a session you watch and one you walk away from" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)) [V]. It describes four gates of increasing strength. The weakest is an in-prompt "run the check and iterate". Next is a `/goal` condition that a separate evaluator re-checks after every turn. Then comes a deterministic Stop hook that blocks the turn from ending until a script passes. The strongest is a verification subagent, "so the agent doing the work isn't the one grading it". The same page adds several working rules. For large features, let Claude interview you and write a self-contained `SPEC.md` that names the files and interfaces, lists what is out of scope, and ends with an end-to-end verification step; then execute it in a fresh session. After two failed corrections, run `/clear` and re-prompt, because "a clean session with a better prompt almost always outperforms a long session with accumulated corrections". It also names five failure patterns: the kitchen-sink session, correcting over and over, the over-specified CLAUDE.md, the trust-then-verify gap, and infinite exploration.

OpenAI's Codex guidance structures each prompt as goal, context, constraints and "done when". It recommends plan mode or an interview for ambiguous work, and lists "giving Codex full permission to your computer before you understand the workflow" as a common mistake ([Codex best practices](https://learn.chatgpt.com/docs/learn/best-practices)) [V]. Cursor calls planning before coding "the most impactful change you can make". It advises reverting and tightening the plan rather than piling on follow-ups, and committing tests that fail before the agent implements "without editing the tests" ([Cursor](https://cursor.com/blog/agent-best-practices)) [V]. AWS Kiro wires the same loop into steering files and hooks, with triggers such as PostFileSave, Stop and PreToolUse ([Kiro steering](https://kiro.dev/docs/steering/); [Kiro hooks](https://kiro.dev/docs/hooks/)) [V].

None of these vendors publishes a controlled comparison showing that its workflow beats plain prompting. The support comes from the indirect experimental evidence in the previous sections and from internal experience.

**Spec-driven development shares one skeleton and no outcome evidence.** GitHub Spec Kit has about 141k stars, reached v1.0.0 on 2026-08-21 and v1.2.0 on 2026-10-13 ([Spec Kit](https://github.com/github/spec-kit)) [V]. Its flow is constitution → specify → plan → tasks → implement → converge. Gates include Test-First ("No implementation code shall be written before" failing tests are approved) and Simplicity. Specs must carry forced `[NEEDS CLARIFICATION]` markers until resolved ([spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)) [V]. Kiro uses `requirements.md`, `design.md` and `tasks.md`, executes independent tasks in "waves", and offers a "Quick Spec" with no approval gates ([Kiro specs](https://kiro.dev/docs/specs/)) [V]. BMAD now routes "small changes straight to build" ([BMAD](https://github.com/bmad-code-org/BMAD-METHOD)) [V]. OpenSpec keeps per-change spec deltas that are archived into living specs, aimed at brownfield code ([OpenSpec](https://github.com/Fission-AI/OpenSpec)) [A].

Each leading tool now offers an escape hatch for small work: Kiro's Quick Spec, BMAD's straight-to-build path, and Spec Kit's independent entry points and bug-fix track. That concedes the main criticism, made by Birgitta Böckeler of Thoughtworks. She saw Kiro turn a small bug fix into 4 user stories with 16 acceptance criteria, found Spec Kit's Markdown volume tedious to review ("rather review code"), and observed agents ignoring instructions or regenerating existing classes as duplicates ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)) [A]. The Thoughtworks Radar placed SDD in "Assess" and warned that "handcrafting detailed rules for AI ultimately doesn't scale" ([Thoughtworks](https://www.thoughtworks.com/radar/techniques/spec-driven-development)) [A].

The only controlled positive result is narrow. Having a test-generation agent first write preconditions, postconditions and undefined behaviours improved bug detection by 9.8 points (p = 0.0352) on Google production bugs ([arXiv 2608.17177](https://arxiv.org/abs/2608.17177)) [PR, SpecOps 2026 workshop]. A June 2026 framework comparison notes the "absence of full-process benchmarks" ([arXiv 2606.04967](https://arxiv.org/abs/2606.04967)) [PP].

**Community packs converge on the same handful of practices.** obra/superpowers (about 299k stars) runs a fixed pipeline: brainstorm with a hard approval gate, then a git worktree with a verified clean test baseline, then a plan of "bite-sized tasks (2-5 minutes each)" with exact file paths and verification steps. Each task goes to a fresh subagent under red-green-refactor TDD, followed by a two-stage review of spec compliance and then code quality. "Critical issues block progress" ([superpowers](https://github.com/obra/superpowers)) [A]. Its brainstorming skill does *not* ask questions when "the request already contains everything that matters". Otherwise it asks one question per message and sizes the work as a quick task, a small change or a project ([SKILL.md](https://raw.githubusercontent.com/obra/superpowers/main/skills/brainstorming/SKILL.md)) [A].

The Karpathy-derived guidelines (about 220k stars) compress the behavioural failures into four rules: think before coding, simplicity first, surgical changes, and goal-driven execution with "loop until verified" ([andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills)) [A]. Three further packs reach the same practices by different routes. **GSD Core** runs every heavy step in a fresh-context subagent and checks that each plan fits a fresh window ([gsd-core](https://github.com/open-gsd/gsd-core)) [A]. **HumanLayer's research → plan → implement** keeps context utilization around 40–60%. It argues that "a bad line of a plan could lead to hundreds of bad lines of code", so human review belongs on research and plans ([HumanLayer](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md)) [A]. **Geoffrey Huntley's "Ralph" loop** reruns one prompt forever, one item per loop, with tests and type checks as "backpressure". He reports placeholder implementations and false "not implemented" conclusions, and says he would not use it on an existing codebase ([ghuntley.com](https://ghuntley.com/ralph/)) [A]. Kent Beck's augmented-coding TDD lets the human choose the next test. He names three warning signs to intervene on: loops, unrequested functionality, and agents "disabling or deleting tests" ([Kent Beck](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes)) [A].

At the criticized end, claude-flow, now Ruflo, advertises queen-led swarm topologies, "100+ specialized agents" and 314 MCP tools. It offers only self-published infrastructure benchmarks and no task-success evidence ([Ruflo](https://github.com/ruvnet/claude-flow)) [A]. None of these packs publishes a controlled with/without comparison. Star counts measure popularity, not effectiveness.

Read across the packs and the vendors, eight practices recur in three or more independent sources. Agents clarify before building, with an explicit skip path for clear requests. They plan in a file that a human reviews, naming exact files and a verification step per task. They work one task or feature at a time in fresh context. They write a failing test first and keep tests immutable during implementation. They show evidence on completion. Review happens in a fresh context, scoped to correctness. Work is isolated in worktrees, with frequent commits as checkpoints. The always-on rules stay small. The overhead critiques concentrate on persona pipelines, many-document specs, swarms and default-loaded toolsets.

**Human oversight works best at intent and outcome, not at every action.** Anthropic's February 2026 field study found the 99.9th-percentile Claude Code turn length roughly doubled in three months, from under 25 to over 45 minutes. Experienced users auto-approve more often (over 40% of sessions against about 20% for new users) but also interrupt more (about 9% of turns against 5%). Claude pauses for clarification more often than humans interrupt it, and more than twice as often on the most complex tasks. Its stop reasons were choosing between approaches (35%), gathering diagnostic information (21%), clarifying vague requests (13%), credentials (12%) and approval before acting (11%) ([Anthropic](https://www.anthropic.com/research/measuring-agent-autonomy)) [V].

Anthropic's internal teams run peripheral features and prototypes asynchronously with auto-accept, but supervise core business logic and critical fixes synchronously. They "commit their state, let Claude work autonomously for 30 minutes, and either accept the solution or restart fresh" ([Anthropic PDF](https://www-cdn.anthropic.com/58284b19e702b49db9302d5b6f135ad8871e7658.pdf)) [V]. The docs warn that "after the tenth approval you're clicking through rather than reviewing" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)) [V].

A method should therefore gate at three points: when the plan is approved, when explicit escalation triggers fire mid-run, and when the evidence and diff are reviewed at the end.
