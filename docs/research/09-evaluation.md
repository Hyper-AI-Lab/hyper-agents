# Evaluate the method on a private, frozen task set it cannot leak

Public leaderboards cannot validate a method, as the first section showed. They are contaminated, their graders are wrong on up to a third of tasks, and they are confounded by harness. The evaluation has to borrow the design of the few 2026 benchmarks that survived scrutiny. DeepSWE authors tasks from scratch and never publishes them upstream. It verifies functionality through public APIs, runs every verifier three times to remove flakiness, ships only a shallow clone, and uses one harness for all models. Its judge disagreed with its verifier on 1.4% of runs, against 32.4% for SWE-bench Pro ([arXiv 2607.07946](https://arxiv.org/html/2607.07946v1)) [PP]. Terminal-Bench 2.0 runs an "Adversarial Exploit Agent" against every task before release ([arXiv 2601.11868](https://arxiv.org/html/2601.11868)) [PP]. SpecBench's held-out tests add no requirements beyond the spec but cover what it implies, such as composition and error handling ([arXiv 2605.21384](https://arxiv.org/html/2605.21384)) [PP]. The Agentic Benchmark Checklist shows that task and reward flaws can mis-estimate performance by up to 100% relative ([arXiv 2507.02825](https://arxiv.org/abs/2507.02825)) [PP].

Anthropic's guidance supplies the operating rules ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)) [V]. Start with 20–50 tasks drawn from real failures. Make each task unambiguous enough that two experts agree on pass or fail, and give each a reference solution. Treat 0% across many trials as a sign the task is broken. Start every trial from a clean environment, because "Claude examined git history from previous trials". Grade outcomes rather than tool-call paths. Report pass^k alongside pass@k: 75% per trial is only about 42% pass^3. Read transcripts too, since fixing a rigid grader once moved Opus 4.5 on CORE-Bench from 42% to 95%.

|---|---|---|
| Task set | 30–60 tasks from the repository's real closed issues, bugs and feature requests, **frozen before any method tuning**. Split into a development set for iterating on the method and a held-out set used only for the final comparison. Tag each task by type (bug, feature, refactor, docs, security-sensitive) and by feature area | [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) [V]; [AI Agents That Matter](https://arxiv.org/abs/2407.01502) [PP] |

| Environment | A clean container per trial, with no production credentials and network access only through an allowlist | [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) [V] |
| Primary metric | **Accepted, regression-free completion.** Hidden tests pass, the full suite passes, there are no unjustified test or CI edits, lint and types are clean, and a blinded reviewer rates the change mergeable. Report pass@1 and pass^3 | [METR](https://metr.org/blog/2025-08-12-research-update-towards-reconciling-slowdown-with-time-horizons/) [PP]; [SWE-CI](https://arxiv.org/abs/2603.03823) [PP] |
| Secondary metrics | Tokens, dollars and wall-clock per *accepted* task; human interventions per task; diff size against the reference; out-of-scope files touched; test and CI tampering rate; false "done" claims (agent reports success, hidden tests fail); safety incidents (destructive commands, sandbox violations, injection-driven actions); post-merge defects over a follow-up window | [HAL](https://arxiv.org/abs/2510.11977v1) [PP]; [Transluce](https://transluce.org/investigating-o3-truthfulness) [PP] |

Hold model, harness version, permissions and budgets constant. Randomize run order. Run at least 3 trials per task per arm | [Miller](https://arxiv.org/abs/2411.00640) [PP] |
| Statistics | Paired per-task differences, with standard errors clustered by feature area (clustered SEs can exceed naive ones by more than 3×). Report the mean difference, SE, CI and between-arm correlation, typically 0.3–0.7 between frontier models. Run a power analysis up front and pre-register metrics. With about 40 tasks × 3 trials, expect to detect only differences of roughly 15–20 points or more | [Anthropic](https://www.anthropic.com/research/statistical-approach-to-model-evals) [V]; [Scale SEAL CIs](https://labs.scale.com/leaderboard/swe_bench_pro_public) |
| Gaming probes | Impossible or conflicting-spec variants of a few tasks, where any pass is cheating; the gap between visible and hidden tests; never using the agent's own report as the outcome | [ImpossibleBench](https://arxiv.org/html/2510.20270v1) [PP]; [SpecBench](https://arxiv.org/html/2605.21384) [PP] |
| Transcript review | Read a random sample of transcripts in every arm; outcome-only scores miss shortcuts and dangerous actions | [arXiv 2605.08545](https://arxiv.org/abs/2605.08545) [PP] |
| LLM judges (rubric dimensions only) | Pairwise rather than pointwise; a thinking model; one judge per dimension with an "Unknown" option; calibrated against humans; never in the same context as the work being judged | [CodeJudgeBench](https://arxiv.org/abs/2507.10535) [PR]; [arXiv 2603.04582](https://arxiv.org/html/2603.04582v1) [PP] |

**The kit itself needs separate checks before any outcome evaluation**, because a skill that never triggers or a hook that never fires silently turns the method off. There are four layers. Static validation uses `claude plugin validate <dir> --strict` (which also checks `.claude/skills`, `.claude/agents` and `.claude/commands`), `skills-ref validate` for open-spec conformance, and the Claude Code settings JSON schema. The load check fails CI when the `system/init` event is missing expected skills or agents, or reports `plugin_errors` or `mcp_server_errors`. Behavioural checks use `claude plugin eval` cases with `tool_used` graders, proving that the verification skill fires on "I'm done" prompts and does not fire on unrelated ones; for Cursor, the same prompts run through `agent -p --output-format json`. Hook unit tests feed captured JSON payloads from *both* tools into each script and assert its exit code and stdout. That last layer catches the subtle failure in which a Cursor permission hook emits nothing and blocks every write, or a Claude Code hook exits 1 and silently lets everything through ([Claude Code plugin evals](https://code.claude.com/docs/en/plugin-evals); [Cursor hooks](https://cursor.com/docs/hooks.md)).

**In production, measure accepted outcomes, not impressions.** Developers in METR's RCT misjudged their own speed by about 40 points ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)) [PP]. The field metrics that the PR studies and DORA tie to real cost cover merge outcomes, stability, review burden and spend. For merge outcomes, track the share of agent PRs merged without modification (54.9% of merged Claude Code PRs in one study), the human-revision rate, and agent-PR CI failure rate and size ([arXiv 2509.14745](https://arxiv.org/abs/2509.14745) [PP]; [arXiv 2601.15195](https://arxiv.org/abs/2601.15195) [PR]). For stability, track reverts and change-failure rate ([DORA](https://dora.dev/research/2025/dora-report/)) [V]. Track review time per PR and cost per merged PR alongside them.

**Every model upgrade calls for a fresh ablation.** Anthropic dropped sprint decomposition and per-sprint QA when Opus 4.6 arrived. It needed context resets for Sonnet 4.5 but not for Opus 4.5 ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)) [V]. The matched-settings study shows planning turning from an accuracy aid into a cost saver as models strengthen ([arXiv 2609.20804](https://arxiv.org/abs/2609.20804)) [PP]. A component that no longer pays on the held-out set should be removed, which is why the method's sixth principle is removability.
