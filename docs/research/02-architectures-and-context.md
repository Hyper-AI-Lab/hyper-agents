# Thin loops won; what still moves results is what the model sees

In 2024, scaffold design produced large relative gains. The peer-reviewed SWE-agent paper measured ablations on SWE-bench Lite with GPT-4 Turbo against an 18.0% baseline ([arXiv 2405.15793](https://arxiv.org/html/2405.15793)) [PR, NeurIPS 2024]:

| Change from the baseline agent | Score | Change |
|---|---|---|
| 30-line file viewer | 14.3% | −3.7 pts |
| Showing the full file | 12.7% | −5.3 pts |
| Paged, grep-like "iterative" search | 12.0% | −6.0 pts |
| Edit command without a lint guardrail | 15.0% | −3.0 pts |
| Full interaction history instead of the last five observations | 15.0% | −3.0 pts |

A 100-line file view and summarized search were the baseline settings, so each row shows what was lost by changing them. The authors distilled four principles: simple actions with few options, compact command sets, concise but informative feedback, and guardrails that stop errors propagating. Two other peer-reviewed systems pushed structure further. Agentless replaced the agent loop with a fixed localize → repair → validate pipeline and solved 32.00% of Lite at about $0.70 per issue ([arXiv 2407.01489](https://arxiv.org/abs/2407.01489)) [PR, FSE 2025]. AutoCodeRover searched over the abstract syntax tree and reached 19% at about $0.43 ([arXiv 2404.05427](https://arxiv.org/abs/2404.05427)) [PR, ISSTA 2024]. CodeAct showed that executable code as the action space beat JSON or text actions by up to 20% across 17 models ([arXiv 2402.01030](https://arxiv.org/abs/2402.01030)) [PR, ICML 2024].

By 2025–2026 most of that elaborate tooling stopped mattering. Anthropic reached 49% on SWE-bench Verified with only two tools, Bash and an exact-match `str_replace` editor, and a short prompt with no enforced workflow ([Anthropic](https://www.anthropic.com/research/swe-bench-sonnet)) [V]. The two design lessons from that work were that **absolute paths** removed a recurring class of errors and that `str_replace` was the most reliable edit method tested. The team reports it "spent more time optimizing our tools than the overall prompt" ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents)) [V].

mini-SWE-agent goes further still: about 100 lines of Python, bash as the only tool and a linear history, scoring above 74% ([GitHub](https://github.com/SWE-agent/mini-swe-agent)) [V]. On the SWE-bench "Bash Only" leaderboard, where every model uses the identical prompt, Claude Opus 4.5 scored 76.8%, Gemini 3 Flash 75.8% and Claude Haiku 4.5 70.0% ([Willison, reading swebench.com](https://simonwillison.net/2026/Feb/19/swe-bench/)) [PP, via secondary]. Live-SWE-agent starts from that bash-only loop and evolves its own tools at runtime, reaching 77.4% on Verified and 45.8% on Pro ([arXiv 2511.13646](https://arxiv.org/abs/2511.13646)) [PP].

The lessons that survived are therefore principles, not tool suites. Keep observations short and high-signal. Guard edits with checks. Use exact-match edits and absolute paths. Let tests be the validator. Aider's measurements show why the edit format itself matters: on 89 refactoring tasks, GPT-4 Turbo went from 20% with search/replace blocks to 61% with unified diffs, because "lazy" placeholder comments dropped roughly threefold. Disabling permissive patch application raised edit errors nine-fold ([Aider](https://aider.chat/docs/unified-diffs.html)) [V]. Claude Code and Cursor already ship exact-match edit tools, so a method gains nothing by inventing its own edit protocol.

What the model sees still matters. In Anthropic's tool-design guidance, a concise response format used 72 tokens where the detailed one used 206, and Claude Code caps tool responses at 25,000 tokens by default. Returning natural-language names instead of UUIDs "significantly improved retrieval precision". Consolidated tools, such as a `search_logs` that returns only the relevant lines, beat raw dumps ([Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents)) [V]. Tool definitions themselves are a context tax. GitHub's MCP server (35 tools) costs about 26K tokens, and five servers with 58 tools cost about 55K. Anthropic's Tool Search, which loads tool definitions on demand, cut that by 85% and *raised* MCP-eval accuracy from 49% to 74% for Opus 4 ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)) [V]. Task Master loads 36 tools, about 21,000 tokens, by default ([README](https://github.com/eyaltoledano/claude-task-master)) [V]. Microsoft now advises coding agents to prefer the Playwright CLI plus Skills over its own MCP server because "CLI invocations are more token-efficient" ([Playwright MCP](https://github.com/microsoft/playwright-mcp)) [V]. Cursor 2.4 made MCP definitions load only when needed for the same reason ([Cursor changelog 2.4](https://cursor.com/changelog/2-4)) [V].

**Context rot** is the best-documented reason to keep context small. Chroma ran 194,480 calls across 18 models and found that performance degrades with input length even on simple tasks. A focused prompt of about 300 tokens beat the full ~113k-token prompt on LongMemEval for *every* model ([Chroma](https://www.trychroma.com/research/context-rot)) [V, technical report]. This updates the U-shaped "lost in the middle" result of 2023 ([TACL](https://arxiv.org/abs/2307.03172)) [PR]: for 2025 models, the needle's position mattered less than input length, distractors and similarity did.

Inside coding agents, the cheapest context hygiene works as well as the clever kind. In the "Complexity Trap" study, simply masking older tool outputs **roughly halved cost** compared with the raw agent, and matched or slightly beat LLM summarization's solve rate across five model configurations. A hybrid of the two saved a further 7–11% ([arXiv 2508.21433](https://arxiv.org/abs/2508.21433v3)) [PR, NeurIPS 2025 DL4C workshop].

Anthropic reports similar gains on an internal agentic-search eval. Clearing stale tool results improved performance by 29%, adding a file-based memory tool on top raised the gain to 39%, and in a 100-turn eval context editing cut token use by 84% ([Anthropic](https://claude.com/blog/context-management)) [V]. Manus calls the KV-cache hit rate "the single most important metric" for a production agent, since cached input costs a tenth as much and agent loops run at roughly 100:1 input to output ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)) [V]. Its recommendations are a stable prompt prefix, append-only context, failed actions left in place so the model updates its beliefs, and "recitation", meaning a rewritten `todo.md` that pushes the plan to the recent end of the context. Manus warns that changing tools mid-session breaks the cache, while Tool Search loads tools dynamically. The two positions reconcile as follows: keep the base prefix stable, and load rarely used tools on demand.

**Localization** works best as agentic search, with embeddings as an optional accelerator. Claude Code's team reportedly dropped a local vector-database RAG for grep-and-glob agentic search because it "outperformed everything else by a lot". Its lead admitted the evidence was "internal vibes" ([OfficeChai](https://officechai.com/ai/claude-researcher-explains-how-agentic-search-performed-better-than-rag-for-code-generation/)) [A].

Cursor's evidence is stronger, though modest. Its embedding model, trained on agent traces, raised offline codebase-question accuracy by 12.5% on average. Online A/B tests showed code retention up 0.3% overall and 2.6% on repositories of 1,000 or more files. Cursor says semantic search combined *with* grep gives the best outcomes ([Cursor](https://cursor.com/blog/semsearch)) [V].

Cognition found that trajectories often spent more than 60% of their first turn just retrieving context. It trained a fast retrieval subagent that returns **files and line ranges, not free-form summaries**, because "over-polluting context hurts more than omitting some context" and summaries can mislead the main agent ([Cognition](https://cognition.com/blog/swe-grep)) [V]. The portable pattern is grep/glob search by default and semantic search for large repositories, with exploration delegated to an isolated helper that returns verifiable pointers.

**Instruction files are obeyed, which is exactly why they are expensive.** The most careful study, from ETH Zurich and LogicStar, has an ICLR 2026 listing ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)) [PP]. It found that AGENTS.md-style context files "generally do not raise task success rates" while raising inference cost by more than 20%. LLM-generated files were slightly harmful, at −0.5% on SWE-bench Lite and −2% on AGENTbench, a figure the paper's introduction gives as −3%. Short developer-written files helped by about 4%.

The mechanism is compliance. When `uv` was mentioned, agents used it about 1.6 times per instance, against under 0.01 when it was not. Every listed requirement becomes extra work. Repository overviews, present in 95–100% of LLM-generated files, did not help agents find the files a PR changed. Generated files helped (+2.7%) only when the repository's other documentation had been removed, which suggests their value is as a substitute for missing docs, not as an addition ([arXiv HTML](https://arxiv.org/html/2602.11988v1)).

Two other studies sharpen the picture. A correlational study of 124 PRs found AGENTS.md associated with 28.64% lower median runtime and 16.58% fewer output tokens, with comparable completion ([arXiv 2601.20404](https://arxiv.org/abs/2601.20404v1)) [PP]. IFScale gave models 500 instructions and found the best frontier models only about 68% compliant, with a bias toward earlier instructions ([arXiv 2507.11538](https://arxiv.org/abs/2507.11538)) [PR, NeurIPS 2025].

The vendors now say the same thing. Claude Code's docs ask, for every line of CLAUDE.md, "Would removing this cause Claude to make mistakes?" and warn that "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)) [V]. Cursor says to add a rule "only when you notice Agent making the same mistake repeatedly" ([Cursor rules](https://cursor.com/docs/rules.md)) [V]. OpenAI's internal Codex-built product used AGENTS.md as a short table of contents into a structured `docs/` directory, not as an encyclopedia ([OpenAI](https://openai.com/index/harness-engineering/); [summary](https://rywalker.com/research/openai-harness)) [V, details via secondary]. GitHub's analysis of more than 2,500 agent files found most fail by being too vague, and that exact commands and explicit boundaries help most ([GitHub blog](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/)) [V].

The rule that follows is to put only non-inferable commands, gotchas and hard boundaries in the always-on file. Procedures go into on-demand skills. Anything that must happen goes into a deterministic hook.

# One writer with many advisers beats parallel writers on coding work

## Parallel writers fail on coupled work; isolated helpers succeed

The only controlled study of agent topology comes from Google Research. It ran 180 configurations across three model families and five architectures, on finance, browsing, planning and workbench tasks; none were coding. **Every multi-agent variant degraded sequential reasoning tasks by 39–70%**. Centralized coordination gained 80.8% on parallelizable tasks. Independent agents amplified errors 17.2× against 4.4× for centralized ones. Once the single-agent baseline exceeded about 45%, coordination gave diminishing or negative returns ([arXiv 2512.08296](https://arxiv.org/abs/2512.08296v2)) [PP].

Anthropic's multi-agent research system shows the other side. An Opus 4 lead with Sonnet 4 subagents beat a single Opus 4 by 90.2% on research queries, at about 15× the chat tokens. Anthropic nevertheless says tasks with few parallelizable steps, "such as most coding work", are not a good fit ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)) [V]. The MAST taxonomy of 1,600+ annotated traces across seven multi-agent frameworks attributes failures mainly to system design and verification gaps, not to model limits; ChatDev was correct only 33.33% of the time ([arXiv 2503.13657](https://arxiv.org/html/2503.13657v3)) [PP].

Cognition's two posts trace how practice settled. In June 2025 it argued that "actions carry implicit decisions". Its example: two subagents building a game's background and its bird produced mismatched styles ([Cognition](https://cognition.com/blog/dont-build-multi-agents)) [V]. In April 2026 it stated the rule that survived: **writes stay single-threaded, and extra agents contribute intelligence, not parallel writes**. Its Devin Review agent catches about 2 bugs per PR, 58% of them severe. It works best when the reviewer shares *no* prior context with the coder and sees only the diff, and the coder filters findings against the user's instructions to avoid loops ([Cognition](https://cognition.com/blog/multi-agents-working)) [V].

Two very large parallel builds show what parallel writing needs to work at all. Cursor coordinated hundreds of agents and found that shared lock files throttled 20 agents to the throughput of 2–3. Flat peer agents became risk-averse and churned. A dedicated integrator role created more bottlenecks than it solved. What worked was a hierarchy: planners create tasks, workers execute without talking to each other, and a judge decides at the end of each cycle whether to continue. Each new iteration starts fresh, because "periodic fresh starts are still needed to combat drift and tunnel vision". The run produced a browser of more than 1M lines, but even the merged migrations "still needed careful review". Cursor concludes that "the harness and models matter, but the prompts matter more" ([Cursor](https://cursor.com/blog/scaling-agents)) [V].

Anthropic built a C compiler with 16 parallel Claude instances, each in its own container, claiming work through lock files in git with no orchestrator. It took about 2,000 sessions and just under $20,000. Parallelism broke down when all agents hit the same bug, until GCC was used as a known-good oracle. The lesson was that "the verifier must be nearly perfect" or the agents solve the wrong problem ([Anthropic](https://www.anthropic.com/engineering/building-c-compiler)) [V].

Anthropic's planner/generator/evaluator harness adds the model-dependence lesson. Out of the box, Claude as QA agent found real issues and then "talked itself into approving them". A full harness turned a broken 20-minute, $9 solo run into a playable game, at 6 hours and $200. With Opus 4.6, sprint decomposition and per-sprint evaluation were removed and only the planner was kept. The authors conclude that "every harness component encodes an assumption about what the model can't do" ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)) [V].

The evidence therefore supports delegation for four kinds of work: read-heavy investigation that would pollute the main context, review or verification in a fresh context, mechanical execution under a clear brief, and truly independent units with their own workspace and an automated oracle. It argues against splitting one design across parallel writers, against delegating serial debugging, and against delegating work the single agent already does well.

## Grounded selection, not more thinking, buys accuracy

The largest reliable gains on top of a good single agent come from **sampling several attempts and selecting with a grounded verifier**. Anthropic's parallel test-time compute discards patches that break the repository's *visible* regression tests and then lets a scoring model choose. That lifted Opus 4 from 72.5% to 79.4% ([Anthropic](https://www.anthropic.com/news/claude-4)) [V] and Sonnet 4.5 from 77.2% to 82.0% ([Anthropic](https://www.anthropic.com/news/claude-sonnet-4-5)) [V]. OpenHands with a trained critic went from 60.6% with one rollout to 66.4% with five ([OpenHands](https://openhands.dev/blog/sota-on-swe-bench-verified-with-inference-time-scaling-and-critic-model)) [V].

The selector has to be trained on realistic data. OpenHands' 4B critic trained on production traces achieved Best@8 of 73.8% against Random@8 of 57.9% on mixed-outcome tasks. Critics trained only on benchmark-style data scored an AUC of 0.45–0.48 on real outcomes, which is no better than chance ([OpenHands](https://openhands.dev/blog/20260305-learning-to-verify-ai-generated-code)) [V].

Other search-based results tell the same story. Tree search (SWE-Search, MCTS with a value agent) gave a 23% relative improvement across five models ([arXiv 2410.20285](https://arxiv.org/abs/2410.20285)) [PR, ICLR 2025]. CodeMonkeys reached 57.4% for about $2,300 using test-based voting ([arXiv 2501.14723](https://arxiv.org/abs/2501.14723)) [PP]. R2E-Gym found that execution-based and execution-free verifiers each plateau around 42–43%, while a hybrid reached 51% ([arXiv 2504.07164](https://arxiv.org/abs/2504.07164)) [PP].

There is a sharp warning attached. With visible tests as the selector, search can actively pick gaming solutions. In SpecBench, the AIDE scaffold chose a lookup-table "C compiler" scoring 97% on visible tests and 0% on held-out ones over a genuine one scoring 53% and 43% ([arXiv 2605.21384](https://arxiv.org/html/2605.21384)) [PP].

Ungrounded self-critique does not deliver comparable gains. Reflexion's ablation showed that reflection depends on executed tests: removing self-generated tests dropped accuracy from 60% to 52% ([arXiv 2303.11366](https://arxiv.org/pdf/2303.11366)) [PR, NeurIPS 2023, via secondary]. Post-hoc self-critique ranking of candidates "did not lead to performance improvements" on LiveCodeBench ([arXiv 2509.22824](https://arxiv.org/pdf/2509.22824)) [PP, via secondary].

More reasoning is not monotonically better either. A study of 4,018 SWE-bench trajectories found that overthinking correlates with failure. Picking the less-overthinking candidate improved performance by almost 30% and cut cost by 43% ([arXiv 2502.08235](https://arxiv.org/abs/2502.08235)) [PP]. Claude Opus 4.5 at *medium* effort matched Sonnet 4.5's best Verified score with 76% fewer output tokens ([Anthropic](https://www.anthropic.com/news/claude-opus-4-5)) [V]. GPT-5-Codex's adaptive reasoning used 93.7% fewer tokens on the easiest tenth of requests and about twice as much effort on the hardest tenth ([Cline](https://cline.bot/blog/gpt-5-codex)) [V, via secondary]. Anthropic's dedicated "think" tool helped in long tool chains (τ-bench airline 0.370 → 0.570), but its December 2025 update recommends interleaved extended thinking instead in most cases ([Anthropic](https://www.anthropic.com/engineering/claude-think-tool)) [V].

**Planning** has the clearest controlled support, with a caveat that shapes the method. "From Plan to Action" analysed 21,120 SWE-agent trajectories across four models on Verified and Pro ([arXiv 2604.12147](https://arxiv.org/abs/2604.12147)) [PP]. Without a plan, agents fell back on internal workflows that were "often incomplete, overfit, or inconsistently applied". A standard plan improved resolution, and periodic plan reminders reduced plan violations. But **"a subpar plan hurts performance even more than no plan at all"**. The matched-settings harness study adds that for strong models, planning saves cost rather than adding accuracy ([arXiv 2609.20804](https://arxiv.org/abs/2609.20804)) [PP]. Plan review is therefore the highest-leverage human checkpoint, and planning should be skipped when, in Claude Code's words, "you could describe the diff in one sentence" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)) [V].

## A strong lead with cheap helpers cuts cost 40–60% if the lead briefs well

Cognition's Devin Fusion pairs a frontier lead that takes "minimal actions" (plan, interpret, delegate, review) with a cheaper sidekick that executes. On Cognition's FrontierCode 1.1 Extended benchmark ([Cognition](https://cognition.com/blog/devin-fusion)) [V]:

| Configuration | Score | Average cost per task |
|---|---|---|
| Fable 5 (xhigh) | 64.9 | $10.53 |
| Opus 5 (medium) | 63.6 | $3.51 |
| Fusion | 63.1 | $1.35 |

Fusion also drives 88% of Cognition's internal merged PRs. Cognition times model switches to coincide with context compaction, which is a cache miss anyway.

A companion study of 3,000 sessions shows that the saving depends on *how* the lead delegates ([Cognition](https://cognition.com/blog/making-fable-cheaper-than-opus)) [V]. Fable 5 costs twice as much per token as Opus 4.8, yet Fable plus a sidekick was 54% cheaper than pure Fable at nearly the same score. The difference was behavioural. Fable delegated early, with briefs listing constraints, edge cases and a definition of done, and asked for a report before commit; it never edited code in 81% of runs. Opus delegated late, dictated whole files, and pulled sidekick output back into its own context twice as often. On the same task, the Fable-written brief produced a result scoring 94 against 25 for the Opus brief. Cognition draws three lessons: forced delegation hurts, delegation has little value for short tasks or serial debugging "where the accumulated context is the work", and an earlier attempt with a *weak* primary model failed ([Cognition](https://cognition.com/blog/multi-agents-working)) [V].

Small models are now close behind on standardized scaffolds. Haiku 4.5 is reported at 73.3% on Verified at $1/$5 per million tokens ([Anthropic](https://www.anthropic.com/news/claude-haiku-4-5)) [V], and at 70.0% against Opus 4.5's 76.8% on the bash-only board ([Willison](https://simonwillison.net/2026/Feb/19/swe-bench/)) [PP, via secondary]. One implementation detail matters here. Claude Code's built-in Explore subagent uses the main conversation's model by default, so cheap exploration needs an explicit `model: haiku` override or `CLAUDE_CODE_SUBAGENT_MODEL` ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents)) [V].

## Long runs survive on files and git, not on the context window

Anthropic's long-running harness found compaction alone insufficient for building a production-quality app across many context windows ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)) [V]. Agents one-shotted features and ran out of context mid-way, later sessions saw progress and declared "victory early", features were marked complete without end-to-end tests, and sessions ended in broken, undocumented states. The fix was an initializer session that writes an `init.sh`, a progress file, a JSON feature list of 200+ items all marked `passes: false`, and an initial commit. JSON was chosen because the model is less likely to tamper with it than with Markdown. Every later session reads `pwd`, the git log and the progress file, starts the app through `init.sh` and runs a smoke test, then takes exactly **one feature**. It verifies that feature end-to-end in a browser, flips only its `passes` flag ("It is unacceptable to remove or edit tests"), commits with a descriptive message and updates the progress file. OpenAI's ExecPlans encode the same idea as a self-contained, restartable plan with living Progress, Surprises & Discoveries, Decision Log and Outcomes sections. "Validation is not optional" ([OpenAI Cookbook](https://developers.openai.com/cookbook/articles/codex_exec_plans)) [V]. OpenAI also claims a similar plan enabled more than seven hours of work from one prompt, a claim without published methodology.

Whether to compact or to reset the context depends on the model. Sonnet 4.5 showed "context anxiety", wrapping up early near its perceived limit, so it needed resets with handoff files. Opus 4.5 ran continuously with compaction ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)) [V]. GPT-5.1-Codex-Max was trained to compact itself across windows for tasks of more than 24 hours ([OpenAI](https://openai.com/index/gpt-5-1-codex-max/)) [V, via secondary]. Handoff files survive model changes and also serve humans, so a portable method keeps them either way.
