# Architectures and research findings behind high-performing autonomous coding agents (2024 – Oct 2026)

Status: COMPLETE (researched 2026-10-14). Claims were checked against the cited page unless marked "secondary", "search summary" or "unverified". Primary pages that could not be fetched: openai.com posts (HTTP 403). Their content is given via secondary sources and flagged.

Evidence labels used below: [PEER] = peer-reviewed venue; [PREPRINT] = arXiv not (yet) peer-reviewed; [VENDOR] = vendor/company-reported; [ANEC] = anecdotal / practitioner blog / talk.

## 1. Agent-computer interfaces (ACIs) and scaffolds: which design decisions produced measurable gains?

### Takeaway
In 2024, ACI/scaffold design produced large relative gains (SWE-agent ablations: −2 to −8 pp from removing individual ACI features on an 18% base; Aider edit format 20%→61% on laziness). By 2025–2026, frontier models in a ~100-line bash-only loop reach 70–77% on SWE-bench Verified, so the lessons that last are the *principles*: tool output that is short and high-signal, guardrails on edits, exact-match edit tools, bounded file views, absolute paths, and tests as the validator. Elaborate tool suites matter less. Same-model harness spreads of roughly 5–20 pp still show up on harder benchmarks (Terminal-Bench 2.0, SWE-bench Pro), but they come from observational leaderboards, not controlled ablations. SWE-bench Verified is now considered contaminated and flawed (OpenAI, Feb 2026).

### Cited Findings
**SWE-agent (Yang et al., NeurIPS 2024) [PEER] — the original ACI ablations**
- Main results (GPT-4 Turbo): 12.47% SWE-bench full, 18.00% SWE-bench Lite; Claude 3 Opus 10.46% / 13.00%. RAG baselines: 1.31% / 2.67% (GPT-4 Turbo). A shell-only agent (no custom ACI) got 11.00% on Lite (7.33% without demonstration) vs 18.00% with the ACI — https://arxiv.org/html/2405.15793
- Ablations on SWE-bench Lite (baseline 18.0%): editing without linting 15.0% (−3.0); no edit command 10.3% (−7.7); *iterative* search (grep-like paged results) 12.0% (−6.0) vs *summarized* search 18.0%; no search 15.7% (−2.3); file viewer 30 lines 14.3% (−3.7), 100 lines 18.0%, full file 12.7% (−5.3); keeping only last 5 observations 18.0% vs full history 15.0% (−3.0); no demonstration 16.3% (−1.7) — https://arxiv.org/html/2405.15793
- Authors' ACI principles: (1) simple actions with few options and concise docs; (2) compact/efficient — consolidate navigation/editing into few actions; (3) informative but concise feedback; (4) guardrails (e.g., syntax checking) to prevent error propagation — https://arxiv.org/html/2405.15793
- Note: "Showing the full file" *hurt* (12.7% vs 18.0%) — early quantitative evidence that more context in the observation can reduce performance — https://arxiv.org/html/2405.15793

**Agentless (Xia et al., UIUC; FSE 2025) [PEER]**
- Three-phase pipeline (localization, repair, patch validation) that avoids letting the LLM choose future actions or use complex tools; FSE listing: 32.67% (98 fixes) on SWE-bench Lite at $0.68; arXiv abstract: 32.00% (96) at $0.70; 1.0 release README: 27.3% (82) at ~$0.34/issue; also introduced SWE-bench Lite-S (problematic issues removed) — https://conf.researchr.org/details/fse-2025/fse-2025-research-papers/85/Demystifying-LLM-based-Software-Engineering-Agents , https://arxiv.org/abs/2407.01489
- Dec 2 2024: Agentless + Claude 3.5 Sonnet 40.7% Lite / 50.8% Verified (README, per search summary); OpenAI's Verified launch (Aug 2024) noted Agentless as the best open-source scaffold, GPT-4o 33.2% on Verified — https://openai.com/index/introducing-swe-bench-verified/
- Agentless-style "discard patches that break visible regression tests, then rank" became the standard selection step in vendor parallel-compute results (Anthropic Sonnet 4.5 82.0%) — https://www.anthropic.com/news/claude-sonnet-4-5

**AutoCodeRover (Zhang et al., ISSTA 2024) [PEER]**
- 19% on SWE-bench Lite, ~$0.43 average cost per issue; works on AST (classes/methods) via code-search APIs rather than raw files; spectrum-based fault localization (SBFL) using tests "further sharpens the context" (no ablation number in abstract) — https://arxiv.org/abs/2404.05427

**CodeAct / OpenHands [PEER]**
- CodeAct (ICML 2024): executable Python code as the unified action space; across 17 LLMs on API-Bank and a new benchmark, up to 20% higher success rate than JSON/text action formats — https://arxiv.org/abs/2402.01030
- OpenHands (ICLR 2025): open platform where agents act by writing code, using a command line and browsing, in sandboxes; supports multi-agent coordination; evaluated on 15 benchmarks incl. SWE-bench and WebArena — https://arxiv.org/abs/2407.16741

**Aider [VENDOR/open-source project, own benchmark]**
- Architect/Editor split (Sep 26 2024, aider code-editing benchmark): o1-preview architect + o1-mini or DeepSeek editor (whole-file format) 85.0% vs o1-preview solo 79.7%; Claude 3.5 Sonnet architect + Claude 3.5 Sonnet editor 80.5% vs solo 77.4%; GPT-4o+GPT-4o 75.2% vs solo 71.4%; gpt-4o-mini pair 60.2% vs solo 55.6%. Rationale: reasoning models are strong at solving but weak at emitting well-formed edit instructions; splitting lets each model focus on one job — https://aider.chat/2024/09/26/architect.html
- Edit format matters for "lazy coding": on 89 Python refactoring tasks, GPT-4 Turbo scored 20% with SEARCH/REPLACE blocks (lazy comments on 12 tasks) vs 61% with unified diffs (lazy on 4 tasks, ~3x less laziness); gpt-4-0613 26%→59%. Design principles: FAMILIAR (git-diff-like), SIMPLE (no escaping/line numbers), HIGH LEVEL (whole functions; without it 30–50% more edit errors), FLEXIBLE (permissive patch application; disabling it raised edit errors 9x) — https://aider.chat/docs/unified-diffs.html
- Repo map: concise list of files + key symbols (classes, functions, signatures, critical lines), ranked with a graph-ranking algorithm over a file-dependency graph to pick the most-referenced identifiers; default budget `--map-tokens` 1k tokens, dynamically expanded when no files are in chat; evidence on the docs page is qualitative only — https://aider.chat/docs/repomap.html

**Anthropic "Building effective agents" (Dec 19 2024) [VENDOR guidance]**
- Distinguishes workflows (predefined code paths) from agents (LLM directs its own process/tools in a loop); patterns: prompt chaining, routing (e.g., easy queries to a cheaper model), parallelization (sectioning or voting), orchestrator-workers, evaluator-optimizer (best with clear evaluation criteria); "use the simplest solution that works, and add complexity only when it measurably improves outcomes"; frameworks can obscure prompts/responses — https://www.anthropic.com/engineering/building-effective-agents
- ACI appendix: give tools as much prompt-engineering effort as the main prompt (examples, edge cases, input requirements, clear boundaries); pick formats easy for the model to write (no line counting/escaping); "poka-yoke" tools; for the SWE-bench agent the team "spent more time optimizing our tools than the overall prompt"; switching to absolute file paths eliminated a recurring error. Coding is a good agent domain because solutions are verifiable via automated tests — same URL

**Anthropic "Writing effective tools for agents — with agents" (Sep 11 2025) [VENDOR guidance]**
- Tool output verbosity: `response_format` enum (concise vs detailed) — concise Slack response 72 tokens vs 206 detailed (~1/3); Claude Code caps tool responses at 25,000 tokens by default; recommend pagination/range/filter/truncation with steering messages; consolidate tools (e.g., `search_logs` returning relevant lines instead of `read_logs`; one `get_customer_context` instead of three getters); namespacing affects accuracy and the best scheme varies by model; returning natural-language names instead of UUIDs "significantly improved retrieval precision"; actionable error messages beat tracebacks — https://www.anthropic.com/engineering/writing-tools-for-agents
- Method: evaluate tools on realistic multi-step tasks with verifiable outcomes and held-out sets; feed eval transcripts to Claude Code to optimize tool descriptions — Claude-optimized tools sometimes beat expert-written ones; Claude 3.5 Sonnet's SWE-bench Verified SOTA came after "precise refinements to tool descriptions" — same URL

**Anthropic minimal scaffold (Jan 6 2025) [VENDOR]**
- Upgraded Claude 3.5 Sonnet: 49% SWE-bench Verified (prior SOTA 45%) with only two tools — Bash and a `str_replace_editor` edit tool — and a short, general prompt (explore, reproduce, edit, verify, edge cases) with no enforced workflow; philosophy: give the model "as much control as possible". Same scaffold: Claude 3.5 Sonnet (old) 33%, Claude 3 Opus 22% — https://www.anthropic.com/research/swe-bench-sonnet
- Tool design lessons: require absolute paths (prevents mistakes after `cd`); `str_replace` was the most reliable edit method tested — it applies only when `old_str` matches exactly one location, else returns an error for retry; detailed tool descriptions tested for misunderstandings. Many successful runs took hundreds of turns and >100k tokens; failure modes include band-aid fixes at the wrong abstraction level and believing success without seeing hidden tests — https://www.anthropic.com/research/swe-bench-sonnet

**Minimal scaffolds catch up (2025–2026)**
- mini-SWE-agent: ~100 lines of Python for the agent class, bash as the only tool, no tool-calling API, linear append-only history, stateless `subprocess.run` per action; claims >74% on SWE-bench Verified; authors: "as LMs have become more capable, a lot of this is not needed at all" — https://github.com/SWE-agent/mini-swe-agent
- SWE-bench "Bash Only" leaderboard (mini-SWE-agent, identical prompt for every model, SWE-bench Verified 500) refreshed Feb 2026: Claude Opus 4.5 (high) 76.8%, Gemini 3 Flash (high) 75.8%, MiniMax M2.5 75.8%, Claude Opus 4.6 75.6%, GLM-5 72.8%, GPT-5.2 (high) 72.8%, Claude Sonnet 4.5 72.8%, Kimi K2.5 71.4%, DeepSeek V3.2 70.8%, Claude Haiku 4.5 70.0% — https://simonwillison.net/2026/Feb/19/swe-bench/ (secondary, reading the official chart at https://www.swebench.com/)
- Live-SWE-agent (arXiv 2511.13646, Nov 2025) [PREPRINT]: starts from a bash-only mini-SWE-agent scaffold and *evolves its own scaffold/tools at runtime* while solving tasks; 77.4% SWE-bench Verified without test-time scaling and 45.8% on SWE-bench Pro, claimed to beat manually crafted agents (model not named in abstract) — https://arxiv.org/abs/2511.13646
- SWE-bench Pro standardized (Scale SEAL) vs vendor numbers [secondary aggregators]: Mar 2026 SEAL snapshot Claude Opus 4.5 45.9%, Sonnet 4.5 43.6%, Gemini 3 Pro 43.3% (overlapping CIs); a Jun 2026 summary says GPT-5.4 (xHigh) 59.1% on the standardized board; aggregator BenchLM (Jul 29 2026, mixing self-reported rows) lists Claude Mythos 5 80.3%, Claude Fable 5 80%, Claude Opus 5 79.2%; aggregator also reports an OpenAI Jul 2026 audit estimating ~30% of the 731-task public Pro split broken — https://www.morphllm.com/swe-bench-pro , https://benchlm.ai/benchmarks/swe-bench-pro (all unverified against primary sources; treat as directional only)
- Scaffold still matters at the margin [secondary, unverified primary]: reported Claude Sonnet 4.5 43.2% on SWE-agent v1 vs 59.8% in Cline's scaffold; Claude Opus 4.5 on SWE-bench Pro 45.9% (SEAL standardized scaffold) vs 50.2% (Cursor) — https://www.morphllm.com/swe-benchmark (aggregator; treat as lead only)

**Benchmark validity (affects how to read all numbers above)**

**Harness vs model on Terminal-Bench 2.0 (Jan 2026) [PREPRINT + leaderboard]**
- Terminal-Bench 2.0: 89 curated terminal tasks, each with its own environment, human reference solution and tests; frontier models+agents scored <65% at publication; error-analysis categories include Disobey Task Specification, Step Repetition, Unaware of Termination Conditions, Context Loss, Premature Termination, No/Irrelevant Verification, Reasoning–Action Mismatch, Weak Verification — https://arxiv.org/abs/2601.11868 , https://arxiv.org/html/2601.11868v1 (ToC/appendix names)

**Claude Code design notes (agentic search vs RAG) [ANEC]**
- Boris Cherny (Claude Code lead) reportedly said early Claude Code used RAG over a local vector DB (Voyage embeddings) and the team switched to agentic search (model runs grep/glob/ls/cat in a loop) because it "outperformed everything else by a lot" — but admitted the evidence was "just 'vibes' – internal vibes"; secondary write-ups add staleness, privacy/security and simplicity as reasons — https://officechai.com/ai/claude-researcher-explains-how-agentic-search-performed-better-than-rag-for-code-generation/ , https://smartscope.blog/en/ai-development/practices/rag-debate-agentic-search-code-exploration/ (secondary; original X post not retrieved)

### Inferences
- The ACI ablations that still transfer to Claude Code/Cursor are about *observation shaping*, not tool count. Bounded views (SWE-agent: 100 lines beat both 30 lines and the full file), summarized search results rather than paged grep dumps, and guardrails at edit time (lint on edit −3 pp when removed) map directly onto hooks (lint or typecheck after Edit) and onto habits like grepping with limits and reading line ranges.
- Exact-match `str_replace` editing (Anthropic) plus a permissive patch applier (Aider's FLEXIBLE principle) are converged best practice. Claude Code and Cursor already provide these, so a method should not invent its own edit protocol.
- Agentless showed that a fixed localize → repair → validate pipeline with regression-test rejection sampling is competitive and cheap. That validation step lives on as the standard selection filter in vendor best-of-N numbers. For an IDE agent, the portable piece is the *validation discipline*: run the existing tests, write a reproduction test, then reject candidates that break visible tests. The no-agent-loop part does not need to carry over.
- "Model > harness" (Terminal-Bench paper headline) and "same model ±15 pp across harnesses" (leaderboards) are both true. Most of the harness spread probably comes from prompts, turn and time budgets, and verification behavior rather than exotic tools. Cursor says outright that "prompts matter more".
- Because Verified is contaminated, any 2026 claim that a scaffold technique adds "+X% on Verified" should be discounted. Pro and Terminal-Bench numbers are the better signal.

### Gaps
- No controlled 2025–2026 ablation (same model, same budget) isolating individual ACI components on a modern benchmark was found; the SWE-agent ablations are from GPT-4 Turbo-era models.
- Aider's repo-map has no published quantitative ablation (docs are qualitative).
- AutoCodeRover's SBFL contribution is not quantified in the abstract; the full paper was not read.
- The Terminal-Bench 2.0 per-harness numbers (Claude Code 58.0% vs ForgeCode 81.8% for Opus 4.6) come from secondary blogs; tbench.ai was not checked directly.
- SWE-bench Pro 2026 leaderboard figures (Mythos 5, Fable 5, Opus 5 ~80%) and the reported July 2026 OpenAI audit of Pro come from aggregators only.
- OpenHands CodeAct 2.x SWE-bench numbers and Moatless Tools cost figures were not retrieved from primary sources.

## 2. Localization and context engineering

### Takeaway
More context reliably hurts once it is unfocused. Chroma found focused ~300-token prompts beat ~113k-token prompts on all 18 models. SWE-agent's full-file view and full history both lost about 3–5 pp. Cognition reports that "over-polluting context hurts more than omitting some context". What works:
- Just-in-time retrieval, with grep/glob agentic search as the backbone, and semantic search added for large repos (Cursor: +12.5% QA accuracy, +2.6% code retention on ≥1k-file repos).
- Exploration offloaded to isolated or fast subagents that return pointers (files and line ranges) or compact summaries.
- Cheap context hygiene, such as observation masking or tool-result clearing, which halves cost with no loss versus LLM summarization.
- A stable, append-only prompt prefix for KV-cache reuse (10x price difference).

### Cited Findings
**Context rot — the empirical basis**
- Chroma "Context Rot" (Jul 14 2025) [tech report]: 18 LLMs (Claude Opus 4/Sonnet 4/3.7/3.5/Haiku 3.5, o3, GPT-4.1, GPT-4o, Gemini 2.5 Pro/Flash, Qwen3 …), 194,480 calls; performance degrades with input length even on simple tasks — models "do not use their context uniformly"; lower needle–question similarity degrades faster; a single distractor hurts and four hurt more; shuffled haystacks beat coherent ones across all 18 models; on LongMemEval, focused prompts (~300 tokens) beat full prompts (~113k tokens) for every model (Claude largest gap, mainly abstentions); GPT models hallucinated most with distractors. Recommendation: separate retrieval from reasoning; pass only relevant context — https://www.trychroma.com/research/context-rot
- Lost in the Middle (Liu et al., TACL) [PEER]: U-shaped performance — highest when relevant info is at the beginning or end, significantly worse in the middle of long contexts even for long-context models (2023 models; Chroma 2025 found needle *position* had no notable effect for 2025 models, while length/distractors/similarity still did) — https://arxiv.org/abs/2307.03172 ; https://www.trychroma.com/research/context-rot
- SWE-agent ablation (2024) shows the same effect inside coding agents: showing the full file 12.7% vs a 100-line window 18.0%; full history 15.0% vs last-5-observations 18.0% (SWE-bench Lite, GPT-4 Turbo) — https://arxiv.org/html/2405.15793

**Anthropic "Effective context engineering for AI agents" (Sep 29 2025) [VENDOR guidance]**
- Context is a finite resource with diminishing returns; each token draws down an "attention budget" (n² pairwise attention); degradation is gradual, not a cliff — https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- System prompt at the "right altitude" (neither brittle hard-coded logic nor vague); start minimal and add instructions based on observed failures; tools self-contained, token-efficient, minimal overlap ("bloated tool sets with ambiguous choices are a common failure mode"); a few diverse canonical examples rather than every edge case — same URL
- Just-in-time retrieval: keep lightweight identifiers (paths, queries) and load data via tools at runtime; Claude Code is hybrid — CLAUDE.md loaded up front, glob/grep just-in-time — same URL
- Long-horizon: (a) compaction — summarize a near-full window, keep architectural decisions, unresolved bugs, implementation details, discard redundant tool output; Claude Code keeps the summary plus the 5 most recently accessed files; tune for recall first then precision; tool-result clearing is the lightest compaction; (b) structured note-taking to files outside the window (Claude Playing Pokémon kept progress notes across thousands of steps and context resets); (c) sub-agents with clean windows that explore with tens of thousands of tokens and return condensed 1,000–2,000-token summaries — same URL

**Manus "Context Engineering for AI Agents" (Jul 18 2025, Yichao 'Peak' Ji) [VENDOR/ANEC]**
- KV-cache hit rate is "the single most important metric" for a production agent; average input:output ratio ~100:1; Claude Sonnet cached input $0.30/MTok vs $3/MTok uncached (10x); keep prompt prefix stable (no second-precision timestamps), append-only context, deterministic serialization — https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus
- Mask, don't remove tools mid-task (changing tool definitions invalidates cache and confuses the model); use consistent tool-name prefixes (`browser_`, `shell_`) to constrain groups — same URL
- File system as unlimited, persistent, restorable context (drop a page but keep its URL/path) — same URL
- Recitation: typical task ~50 tool calls; agent rewrites a todo.md to push the global plan into the recent end of context, countering drift / lost-in-the-middle — same URL
- Keep failed actions and error traces in context so the model updates beliefs; vary serialization to avoid few-shot pattern lock-in (e.g., repetitive drift reviewing 20 resumes) — same URL

**Compaction strategy for coding agents — simple beats clever**
- "The Complexity Trap" (Lindenbauer et al., JetBrains Research/TUM, arXiv 2508.21433; NeurIPS 2025 DL4C workshop) [PEER-workshop]: within SWE-agent on SWE-bench Verified across five model configurations, simple *observation masking* (hiding older tool outputs) roughly halves cost vs the raw agent while matching and sometimes slightly exceeding LLM summarization's solve rate (e.g., Qwen3-Coder 480B 53.8% raw → 54.8% masked, per search snippet of v2); a hybrid cuts cost a further 7% vs masking and 11% vs summarization; preliminary evidence it generalizes to OpenHands — https://arxiv.org/abs/2508.21433v3 , https://neurips.cc/virtual/2025/131688
- Consistent with SWE-agent's 2024 ablation (keep last-5 observations 18.0% vs full history 15.0%) and Anthropic's "tool-result clearing is the lightest form of compaction" — https://arxiv.org/html/2405.15793 , https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

**Search/localization: grep-style agentic search vs embeddings**
- Cognition SWE-grep (Oct 16 2025) [VENDOR]: in Windsurf/Devin, trajectories often spent >60% of their first turn retrieving context; RL-trained retrieval subagents issue up to 8 parallel tool calls per turn for max 4 turns (vs 10–20 serial turns for typical agentic search); SWE-grep-mini >2,800 tok/s, SWE-grep >650 tok/s on Cerebras (~20x / 4.5x Haiku 4.5's ~140 tok/s); scored by weighted F1 (β=0.5, precision-weighted) on an internal CodeSearch eval, claimed to match frontier models; with Sonnet 4.5 as main model it completed the same number of hard SWE-bench Verified tasks in significantly less end-to-end time. Rationale: "over-polluting context hurts more than omitting some context"; subagent returns files + line ranges, not free-form summaries (summaries can mislead the main model) — https://cognition.com/blog/swe-grep
- Cursor semantic search (Nov 6 2025) [VENDOR]: custom embedding model trained on agent-session traces; offline (Cursor Context Bench) average +12.5% accuracy answering codebase questions (range 6.5–23.5% across models, all frontier models gained); online A/B: +0.3% code retention overall, +2.6% on codebases with ≥1,000 files; without semantic search, dissatisfied follow-ups +2.2%; semantic search used *alongside* grep — "the combination of these two leads to the best outcomes" — https://cursor.com/blog/semsearch
- Contrast: Claude Code dropped vector-DB RAG for pure agentic search on internal "vibes" (see §1) — https://officechai.com/ai/claude-researcher-explains-how-agentic-search-performed-better-than-rag-for-code-generation/
- AutoCodeRover's AST-structured search (classes/methods) + SBFL and Aider's ranked repo map (default 1k tokens) are the 2024 structured-localization approaches — https://arxiv.org/abs/2404.05427 , https://aider.chat/docs/repomap.html

### Inferences
- The Claude Code vs Cursor disagreement on embeddings is mostly about deployment. Claude Code's evidence is "vibes". Cursor's is an A/B test with small but real gains, and those gains concentrate in large repos and come from semantic search *combined with* grep. A method running in both IDEs should treat semantic search as an optional accelerator for big codebases, with grep/glob as the default.
- The strongest portable context practices are cheap. Isolate exploration in a read-only subagent that returns file:line pointers plus a short summary (Anthropic: 1–2k tokens; Cognition: line ranges). Clear or mask old tool outputs. Keep tool outputs bounded, with logs written to files and grepped (C compiler harness). Push the current plan to the end of context with a todo file that gets rewritten as work progresses (Manus recitation).
- Summaries from subagents can mislead the main agent (Cognition). Asking subagents for verifiable pointers (paths, line ranges, quoted snippets) rather than conclusions reduces this risk.
- Manus' KV-cache lesson argues against dynamic tool sets and editing the system prompt mid-session. Anthropic's Tool Search Tool takes the other side: defer-loading tools cut 85% of definition tokens and *raised* accuracy. The two can be reconciled. Load rarely used tools on demand through search, and keep the base prefix stable.

### Gaps
- No controlled study comparing grep-only vs embedding-augmented search inside the same coding agent on a public benchmark was found (Cursor's Context Bench is internal).
- Quantitative effect of repo maps / codemaps (Aider, Windsurf Codemaps) on modern agents remains unmeasured in public sources.
- Chroma tested retrieval-style tasks, not agentic coding trajectories. Context-rot curves specific to coding agents (accuracy vs context fill on SWE tasks) were not found beyond SWE-agent's 2024 ablation and the Complexity Trap paper.
- Exact numeric solve rates in the Complexity Trap abstract were not shown; the 53.8%→54.8% figure comes from a search snippet of v2.

## 3. Single-agent vs multi-agent; delegation, parallel agents, reviewer/verifier agents

### Takeaway
For coding, the evidence favors a single writer thread with helper agents that contribute intelligence: read-only exploration, review with fresh context, planning, and verification. Parallel writers that coordinate as peers do poorly. The one controlled study (Google, 180 configs, non-coding) found every multi-agent variant degraded sequential tasks by 39–70%, while centralized coordination gained +80.8% on parallelizable ones. Independent agents amplified errors 17.2x. Parallel writing does work at scale in one specific shape: hierarchical planner → isolated workers → judge, with separate workspaces and a near-perfect automated verifier (Cursor's browser, Anthropic's C compiler). Even then, both report frequent conflicts, drift, and the need for fresh restarts and human review. The cost is ~4x (single agent) to ~15x (multi-agent) chat tokens.

### Cited Findings
**The 2025 "don't" position — Cognition (Jun 12 2025, Walden Yan) [VENDOR opinion]**
- Two principles: (1) "share context, and share full agent traces, not just individual messages"; (2) "actions carry implicit decisions" — conflicting implicit assumptions between agents produce bad results. Flappy Bird example: background subagent builds a Super-Mario-style background, bird subagent builds a mismatched bird; passing the original task to each doesn't fix it — https://cognition.com/blog/dont-build-multi-agents
- Recommended: single-threaded linear agent; for long tasks add a history-compression model (Cognition fine-tuned smaller models for this). Claude Code subagents described approvingly as answering well-defined questions, not writing code, never running in parallel with the main agent — keeps investigative work out of the main history. 2024-era edit-apply split (big model writes edit description, small model applies) was "often faulty"; edit decision + application now usually one model — same URL

**Anthropic multi-agent research system (Jun 13 2025) [VENDOR]**
- Opus 4 lead + Sonnet 4 subagents beat single-agent Opus 4 by 90.2% on an internal research eval; agents use ~4x chat tokens, multi-agent ~15x; on BrowseComp three factors explain 95% of variance, token usage alone 80% (plus tool-call count and model choice); parallel tool calling cut research time up to 90%; a tool-testing agent rewriting a tool description cut later task-completion time 40%; ~20 eval queries were enough to start — https://www.anthropic.com/engineering/multi-agent-research-system
- Explicitly *not* a good fit: tasks with few parallelizable steps "such as most coding work", domains where all agents need the same context, many inter-agent dependencies, low-value tasks (token cost), real-time coordination — same URL
- Delegation needs objective, output format, tool/source guidance and clear boundaries (vague instructions caused duplicated searches); effort-scaling rules in the prompt: simple fact-finding 1 agent / 3–10 tool calls, comparisons 2–4 subagents / 10–15 calls each, complex research >10 subagents; subagents write outputs to a filesystem and pass lightweight references to avoid "game of telephone" loss and token copying; lead saves plan to memory because >200k context gets truncated — same URL

**Controlled study — Google Research "Towards a Science of Scaling Agent Systems" (Kim et al., arXiv 2512.08296, Dec 2025, v3 Apr 2026) [PREPRINT]**
- 180 controlled configurations, 3 LLM families, 5 architectures (single agent; Independent, Centralized, Decentralized, Hybrid multi-agent) on Finance-Agent, BrowseComp-Plus, PlanCraft, Workbench (no coding benchmark): on sequential reasoning tasks *all* multi-agent variants degraded performance 39–70%; centralized coordination +80.8% on parallelizable tasks; decentralized +9.2% on web navigation; independent agents amplify errors 17.2x vs 4.4x for centralized; coordination gives diminishing/negative returns once single-agent baseline exceeds ~45%; tool-heavy tasks suffer disproportionately from multi-agent overhead under fixed budgets; predictive model picks best strategy for 87% of held-out configs (R² 0.524), 4/5 principles held on GPT-5.2 — https://arxiv.org/abs/2512.08296v2 ; blog https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/

**The 2026 revision — Cognition "Multi-Agents: What's Actually Working" (Apr 22 2026, Walden Yan) [VENDOR]**
- What changed: models became more agentic at tool use, managing context limits and passing distilled context; enterprise Devin usage ~8x in 6 months; but cited big demos (200k-LOC browser, 100k-LOC C compiler, 10k+-iteration training-script optimization) all had simple verifiable success criteria unlike most real software — https://cognition.com/blog/multi-agents-working
- Core rule: writes stay single-threaded; extra agents contribute intelligence, not parallel writes — same URL
- Review loop: Devin Review catches ~2 bugs/PR on average, ~58% severe (logic errors, missing edge cases, security); works best when coder and reviewer share *no* prior context (reviewer sees only the diff, avoiding context rot from the long coding session); coder filters findings against user instructions to prevent loops/out-of-scope work — same URL
- "Smart friend": SWE-1.5 (~950 tok/s) primary + Sonnet 4.5 for planning in Windsurf; mitigations: force ≥1 consultation, train/prompt when to escalate, domain rules (always escalate merge conflicts), share a forked full context, let the smart model push back; result: SWE-1.5 too weak as primary (bad at knowing when/what to escalate); cross-frontier pairing (Claude + GPT) gave real gains on hardest scenarios as a *capability router* rather than difficulty escalator — same URL
- Hierarchical delegation is live: manager Devin spawns child Devins coordinated via internal MCP ("map-reduce-and-manage"); failure modes: managers overly prescriptive without codebase context, agents wrongly assume shared state with children, children don't report back by default. Parallel-writer swarms and unstructured agent negotiation still "mostly a distraction" — same URL

**Hundreds of parallel agents — Cursor "Scaling long-running autonomous coding" (Jan 14 2026, Wilson Lin) [VENDOR case study]**
- Coordination designs that failed: (a) shared coordination file with locks — locks held too long / never released, 20 agents ran at the effective throughput of 2–3, brittle; (b) optimistic concurrency control — simpler/more robust but didn't fix deeper problems; (c) flat peers with no hierarchy — agents became risk-averse, avoided hard tasks, made small safe changes, churned. An "integrator" role for QC/conflict resolution was removed because it created more bottlenecks than it solved — https://cursor.com/blog/scaling-agents
- What worked: planners continuously explore and create tasks (can spawn sub-planners per area); workers execute assigned tasks without coordinating with each other and push; a judge decides at the end of each cycle whether to continue, and the next iteration starts *fresh* ("periodic fresh starts are still needed to combat drift and tunnel vision") — same URL
- Results: web browser from scratch ~1 week, >1M LoC across ~1,000 files, hundreds of concurrent workers; Solid→React migration in Cursor's codebase over 3 weeks (+266K/−193K) passing CI but "still needed careful review"; video-rendering rewrite 25x faster (merged); ongoing Java LSP (550K LoC), Windows 7 emulator (1.2M LoC), Excel (1.6M LoC); trillions of tokens — same URL
- Model-by-role: GPT-5.2 much better at extended autonomous work (instruction following, focus, less drift); Opus 4.5 "tended to stop earlier and take shortcuts"; GPT-5.2 a better planner than coding-specialized GPT-5.1-Codex; "The harness and models matter, but the prompts matter more" — same URL

**Multi-agent failure taxonomy — MAST (Cemri et al., "Why Do Multi-Agent LLM Systems Fail?", arXiv 2503.13657, 2025) [PREPRINT; venue unverified]**
- 14 failure modes in 3 categories — system design/specification issues, inter-agent misalignment, task verification — from 1,600+ annotated traces across 7 MAS frameworks; ChatDev only 33.33% correct on their ProgramDev benchmark; failures stem mainly from orchestration/design rather than solely model limits; verifier gap (e.g., checking code compiles but not that it meets the request) — https://arxiv.org/html/2503.13657v3 , https://sky.cs.berkeley.edu/project/mast/ (44.2% "system design" share from a secondary summary — unverified)

**Reviewer/verifier agents in production — Cognition 2025–2026 [VENDOR]**
- Devin Review (Jan 2026) + autofix loop: reviewer flags bugs and Devin fixes until the diff comes back clean; ~2 bugs/PR, ~58% severe (see above) — https://cognition.com/blog/multi-agents-working , https://cognition.com/blog/testing-development
- "Verifying Agentic Development at Scale" (May 29 2026): Devin tests its own changes by running the app on a VM with computer-use; writes a *source-grounded test plan* first (models otherwise assumed nonexistent app paths); annotates each test with assertions marked passed/failed/untested, to reduce rationalizing unexpected results / claiming unverified results; repeated steps (login) as deterministic scripts in a repo "testing skill" ("decrease flakiness dramatically", no figure); failure modes: over-testing unrelated areas, setup rabbit-holes, missing the core changed behavior, mistimed screenshots, "cheating" by running JS to trigger states; engineers ran 10–20 Devins in parallel, each with own dev server; no accuracy numbers — https://cognition.com/blog/testing-development
- Devin 2025 performance review (Nov 14 2025): PR merge rate 67% (vs 34% a year earlier), ~4x faster problem solving, ~2x resource efficiency; best fit = clear upfront requirements + verifiable outcomes, ~4–8 junior-engineer-hours; struggles with ambiguous open-ended work and *mid-task requirement changes*; better codebase understanding (auto-generated docs/diagrams) was a major driver of the merge-rate gain; "code quality is not straightforwardly verifiable" so human review remains — https://cognition.com/blog/devin-annual-performance-review-2025

**Parallel agents in separate workspaces — Anthropic C compiler (Feb 5 2026, Nicholas Carlini) [VENDOR case study]**
- 16 parallel Claude Opus 4.6 instances, ~2,000 Claude Code sessions over ~2 weeks, ~2B input / 140M output tokens, just under $20,000; produced a ~100k-line Rust C compiler that builds Linux 6.9 on x86, ARM and RISC-V — https://www.anthropic.com/engineering/building-c-compiler
- Coordination was deliberately minimal: each agent in its own Docker container cloning a shared bare git repo; work claimed by writing a lock file in `current_tasks/` (git sync forces a collision loser to pick another task); pull/merge/push then remove the lock; merge conflicts frequent; a bash loop restarts sessions; *no orchestrator agent and no other inter-agent communication* — same URL
- Parallelism broke down when all agents hit the same Linux-kernel bug and overwrote each other's fixes; fixed by using GCC as a known-good oracle (compile most files with GCC, a subset with the new compiler) so agents could work on different failures; delta debugging later — same URL
- Test/harness lessons: the verifier must be nearly perfect or Claude solves the wrong problem; CI added to stop regressions ("new features often broke existing functionality"); minimize context pollution (print a few lines, log details to files, put "ERROR" on the same line for grep, precompute summary stats); `--fast` mode runs a deterministic per-agent 1%/10% test sample to cope with "time blindness"; agents maintain READMEs/progress files to re-orient in fresh containers; specialized roles (dedupe, compiler perf, generated-code efficiency, Rust-quality critic, docs) — same URL

**Planner / generator / evaluator — Anthropic "Harness design for long-running application development" (Mar 24 2026, Prithvi Rajasekaran) [VENDOR case study]**
- Three agents (Claude Agent SDK + Playwright MCP): planner expands a 1–4 sentence prompt into a product spec (deliverables, not granular technical detail, to avoid cascading spec errors); generator builds with git; evaluator clicks through the running app, tests UI/API/DB state against hard per-criterion thresholds and fails the sprint with detailed feedback. "Sprint contracts": generator proposes scope + verification, evaluator reviews, iterate to agreement; agents communicate through files (e.g., Sprint 3 had 27 criteria) — https://www.anthropic.com/engineering/harness-design-long-running-apps
- Out of the box Claude was a weak QA agent — found real issues then "talked itself into approving them", tested superficially; calibration needed few-shot score breakdowns and several rounds of prompt revision against the author's judgment. Rationale for separating roles: models are lenient grading their own work — same URL
- Retro game maker (Opus 4.5): solo run 20 min / $9 → broken core play mode; full 3-agent harness 6 h / $200 → playable game (>20x cost). DAW (Opus 4.6, simplified harness): 3 h 50 min, $124.70 total (planner $0.46; three build rounds $71.08/$36.89/$5.88; three QA rounds $3.24/$3.09/$4.06) — same URL
- With Opus 4.6, sprint decomposition was removed (builder ran coherently >2 h), per-sprint evaluation replaced by a single final QA pass; evaluator "worth its cost only for tasks beyond what the model handles reliably alone"; planner retained (without it the generator under-scoped). Lesson: "every harness component encodes an assumption about what the model can't do" — remove components one at a time when models change — same URL

### Inferences
- Delegation pays off for coding in these cases:
  - Read-heavy, parallelizable investigation that would otherwise pollute the main context (Anthropic, Cognition, Claude Code docs).
  - Review or verification by an agent with *fresh* context that sees only the diff and the criteria (Devin Review ~2 bugs/PR, 58% severe; Claude Code writer/reviewer; the Anthropic evaluator).
  - Mechanical, well-specified execution handed to a cheaper sidekick under a strong lead (Fusion).
  - Truly independent work units, each in its own worktree with an automated oracle (C compiler, Cursor).
- Delegation hurts in these cases:
  - Sequential, tightly coupled edits.
  - Serial debugging, where "the accumulated context is the work".
  - Splitting one design across parallel writers (Flappy Bird).
  - Tasks the single agent already handles well (Google: coordination returns diminish or turn negative once the single-agent baseline exceeds ~45%).
  - Delegation forced on a lead that doesn't trust or brief the worker well.
- Reviewer agents need explicit scoping. Claude Code's docs warn that a reviewer told to find gaps will always find some, which leads to over-engineering. Cognition filters reviewer findings against user instructions.
- Lightweight coordination via git plus lock files works for a handful of agents (16 in the C compiler). Cursor found locks bottlenecked at 20+ (throughput of 2–3) and moved to hierarchy. For an IDE method, worktree-isolated subagents with one integrating lead is the practical ceiling.
- The fact that Opus 4.5 "stopped earlier and took shortcuts" in Cursor's runs, while GPT-5.2 drifted less, suggests that model-specific persistence matters for long autonomous runs. Harness components such as judges, feature lists and stop hooks compensate for it.

### Gaps
- No controlled single- vs multi-agent comparison on a *coding* benchmark (SWE-bench Pro, Terminal-Bench) with equal token budgets was found; Google's study excluded coding, and vendor case studies lack baselines (except Anthropic's solo vs harness game-maker anecdote).
- MAST per-mode failure rates for coding MAS (ChatDev, MetaGPT) were not retrieved; the 44.2% figure is unverified.
- No public numbers on the precision of reviewer agents (false-positive rate of Devin Review / Claude Code review) were found.
- Claude Code "agent teams" (experimental) have no published evaluation found.
- Cognition's 2026 hierarchical-delegation results ("week-long tasks spanning multiple PRs") have no quantitative success rates.

## 4. Planning and reasoning (planner/executor, thinking effort, search/best-of-N, reflection)

### Takeaway
The most reliable SWE-specific gains come from *grounded* selection and verification, not from same-context self-reflection.
- Parallel attempts filtered by visible regression tests and then ranked by a scorer or critic add about 5–16 pp: Sonnet 4.5 77.2%→82.0%; OpenHands 60.6%→66.4% with a trained critic; OpenHands Best@8 73.8% vs Random@8 57.9% on mixed-outcome tasks; MCTS +23% relative.
- More thinking is not monotonically better. Overthinking correlates with failure (picking low-overthinking runs gave +~30% with −43% cost). Opus 4.5 at medium effort matched Sonnet 4.5's best with 76% fewer tokens. Adaptive effort (GPT-5-Codex) is the current pattern.
- Explicit planning helps when scope is uncertain or spans multiple files, and should be skipped for one-sentence diffs. Planner/executor role splits keep earning their place at long horizons, because without a planner the generator under-scopes.

**Tree search / best-of-N with verifiers**

### Inferences
- In a single IDE agent, best-of-N can be approximated cheaply. Have the agent write or run a reproduction test, then reject any change that breaks existing tests. For high-stakes changes, spawn 2–N worktree-isolated attempts and pick using test results plus a fresh-context reviewer. The evidence says the selector must be grounded (tests or a trained critic). Prompt-based reranking was beaten by a trained critic (OpenHands), and post-hoc self-critique on final answers did not help (Critique-Coder).
- Reasoning effort should be adaptive. Use high effort for planning, ambiguous diagnosis and review. Use lower effort or cheaper models for mechanical execution. Watch for "analysis paralysis" and "premature disengagement" (overthinking taxonomy). A turn or time budget combined with an objective stop check (tests pass) guards against both.
- The "think" tool's value has been absorbed by interleaved extended thinking (Anthropic Dec 2025 update), so a separate think tool is unnecessary on current Claude models.
- Same-context "reflect on your answer" steps have weak SWE evidence. Reflection grounded in execution feedback is what the evidence supports: test failures, lint and type errors, screenshots.

### Gaps
- No public, controlled measurement of plan mode or explicit planning on a coding benchmark (plan vs no-plan, same model) was found; evidence is vendor guidance and case studies.
- No SWE-bench ablation cleanly isolating un-grounded self-reflection was found.
- Exact sample counts (N) behind Anthropic's parallel test-time compute scores are not disclosed.
- OpenAI GPT-5-Codex primary page was inaccessible (403); adaptive-reasoning numbers come via secondary sources.
- Claude Opus 4.5's absolute SWE-bench Verified number was only in a chart image on the announcement page (not extracted).

## 5. Memory and state (instruction files, progress files, checkpoints, long-horizon resumption)

### Takeaway
Instruction files are obeyed, which is exactly why they are costly. The best controlled study (ETH, 2026) found AGENTS.md-style files do not raise success, add more than 20% cost, and that overviews don't help localization. LLM-generated files are slightly harmful (−0.5% to −3%). Short, human-written, non-obvious requirements give a small gain (~+4%). A correlational study found ~29% lower runtime with AGENTS.md present. Adherence also decays as instruction count grows (IFScale: ~68% at 500 instructions). The conclusion is to keep instruction files minimal and push the rest to on-demand skills or docs, or to deterministic hooks.

For long-horizon work, the evidence-backed state pattern is externalized, structured state:
- A JSON feature/test list the agent may only tick.
- A progress log plus git commits.
- An init/smoke-test script run at the start of every session.
- One feature per session.
- File-based memory plus clearing of stale tool results (+39% on Anthropic's internal eval).
- Compaction, which is now increasingly trained into the models (Codex-Max, Opus 4.5+).

### Cited Findings
**Instruction/context files (AGENTS.md / CLAUDE.md) — controlled studies**
- Gloaguen et al. (ETH Zurich / LogicStar), "Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?" arXiv 2602.11988 (v1 Feb 12 2026, v3 Sep 29 2026) [PREPRINT; an ICLR 2026 virtual listing exists]: context files "generally do not raise task success rates" while raising inference cost >20% on average, across LLMs/agents and for both LLM-generated and developer-written files; agents *do* follow the instructions; repository overviews "do not help" — https://arxiv.org/abs/2602.11988 ; listing https://iclr.cc/virtual/2026/10021235
- Detail (v1 HTML): LLM-generated files −0.5% (SWE-bench Lite) and −2% (AGENTbench, 138 tasks from niche repos; intro says −3%); developer-written files ~+4% on AGENTbench (better than none for all agents except Claude Code); LLM files add ~2.45 / 3.92 steps and ~20% / 23% cost; e.g., Claude Code + Sonnet 4.5 on AGENTbench 40.7→46.5 steps, $1.15→$1.33; Codex + GPT-5.2 $0.38→$0.57; reasoning tokens +14–22% for GPT-5.2 — https://arxiv.org/html/2602.11988v1
- Same paper: instructions are obeyed strongly (`uv` used ~1.6x/instance when mentioned vs <0.01 when not; repo-specific tools ~2.5x vs <0.05) — so every listed requirement becomes extra work; overviews did not reduce steps to reach the files changed by the PR; overviews present in 8/12 developer files and 95–100% of LLM-generated files (Sonnet 4.5, GPT-5.2, Qwen3); when existing docs were removed, LLM files *helped* ~+2.7% (they substitute for missing docs); stronger models don't write better context files. Recommendation: omit LLM-generated context files for now; keep human-written ones to minimal requirements such as repo-specific tooling — https://arxiv.org/html/2602.11988v1
- Lulla et al., "On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents" arXiv 2601.20404 (Jan 28 2026, v2 Mar 30 2026) [PREPRINT]: 10 repos, 124 GitHub PRs, with vs without AGENTS.md: median runtime −28.64%, output tokens −16.58%, "comparable task completion behavior"; correlational, efficiency-only — https://arxiv.org/abs/2601.20404v1
- Reconciliation (inference, see Inferences): the two studies measure different things (efficiency on PRs with existing human AGENTS.md vs success on issue-resolution); both are consistent with "short, human-written, non-obvious requirements help; overviews and generated boilerplate cost tokens without improving success".

**Instruction count vs adherence**
- IFScale (Jaroslawicz et al., Distyl AI, NeurIPS 2025, arXiv 2507.11538) [PEER]: 500 keyword-inclusion instructions in a report-writing task, 20 models / 7 providers; best frontier models only ~68% accuracy at 500 instructions; three decay shapes — threshold (reasoning models o3, Gemini 2.5 Pro: near-perfect until a critical density then rising variance), linear (GPT-4.1, Claude Sonnet 4), exponential (GPT-4o, Llama 4 Scout); bias toward earlier instructions — https://arxiv.org/abs/2507.11538 , https://neurips.cc/virtual/2025/122417 ; a later Arize blog claims newer models are "an order of magnitude better" (secondary) — https://arize.com/?p=28407

**OpenAI "Harness engineering" (Feb 11 2026, Ryan Lopopolo) [VENDOR; primary page 403 to fetcher — details via secondary]**
- Internal product built with zero manually written code (app logic, tests, CI, docs, observability, tooling all by Codex) in ~1/10th the estimated time; humans "steer", agents execute; main engineering job becomes designing environments, specifying intent and building feedback loops — https://openai.com/index/harness-engineering/ (title/date/claims confirmed via search snippets)
- [secondary] AGENTS.md used as a short table of contents pointing into a structured `docs/` directory rather than an encyclopedia; ~1,500 PRs merged in five months, ~3.5 PRs/engineer/day, team grew 3→7 — https://rywalker.com/research/openai-harness , https://yage.ai/share/harness-engineering-survey-en-20260312.html

**Claude Code official best practices (docs, current as of Oct 2026) [VENDOR guidance]**
- Core constraint stated: "Claude's context window fills up fast, and performance degrades as it fills" — https://code.claude.com/docs/en/best-practices
- CLAUDE.md: loaded every session, so include only broadly applicable things; keep it short; per line ask "Would removing this cause Claude to make mistakes?"; "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!"; include non-guessable bash commands, non-default style rules, test runners, repo etiquette, project-specific architectural decisions, env quirks, gotchas; exclude what can be read from code, standard conventions, detailed API docs (link instead), frequently changing info, file-by-file descriptions; use emphasis ("IMPORTANT") on one line only; occasional-use knowledge goes into on-demand *skills*; deterministic must-happen actions go into *hooks* (CLAUDE.md is advisory) — same URL
- Verification first: "Give Claude a check it can run" (tests, build exit code, linter, fixture diff, screenshot); gate the stop via prompt, `/goal` (separate evaluator re-checks every turn), a Stop hook (deterministic), or a verification subagent so "the agent doing the work isn't the one grading it"; ask for evidence (test output, commands, screenshots) rather than assertions — same URL
- Explore → plan (plan mode) → implement → commit; plan mode adds overhead — skip when "you could describe the diff in one sentence"; for larger features have Claude interview you, write SPEC.md, then execute in a *fresh session* — same URL
- Session hygiene: `/clear` between unrelated tasks; after two failed corrections, clear and re-prompt ("a clean session with a better prompt almost always outperforms a long session with accumulated corrections"); steer compaction (`/compact <focus>`, CLAUDE.md "when compacting, preserve modified files and test commands"); checkpoints/rewind snapshot files edited via Claude's edit tools only (not Bash changes) — "not a replacement for git"; named sessions, `--continue/--resume` — same URL
- Failure patterns listed: kitchen-sink session, correcting over and over, over-specified CLAUDE.md, trust-then-verify gap, infinite exploration (unscoped investigation reading hundreds of files) — same URL

**Compaction trained into the model — OpenAI GPT-5.1-Codex-Max (Nov 2025) [VENDOR via secondary]**
- Codex compacts the session near the window limit giving a fresh window, repeating until the task is done; OpenAI observed >24 h tasks internally; 77.9% SWE-bench Verified vs 73.7% for GPT-5.1-Codex (high); ~30% fewer *thinking* tokens than GPT-5.1-Codex at the same SWE-bench Verified score — https://openai.com/index/gpt-5-1-codex-max/ (via https://the-decoder.com/openai-releases-gpt-5-1-codex-max-to-handle-engineering-tasks-that-span-twenty-four-hours/ , https://www.neowin.net/news/openai-announces-gpt51-codex-max-a-new-coding-model-built-for-long-running-tasks/)

**Long-horizon harness state (Anthropic, Nov 26 2025) [VENDOR, qualitative]**
- Compaction alone was not enough: Opus 4.5 looping across context windows fell short of a production-quality web app from a high-level prompt. Fix: an *initializer* session (same tools/system prompt, different first user prompt) writes `init.sh`, `claude-progress.txt`, a comprehensive feature list (>200 features for a claude.ai clone, each with category/description/test steps/`passes:false`) and an initial git commit; every later *coding* session makes incremental progress on one feature, commits with descriptive messages, updates the progress file — https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
- Feature list in JSON because the model is less likely to inappropriately overwrite JSON than Markdown; agents may only flip `passes`, and are forbidden to remove/edit tests — same URL
- Session-start routine: `pwd`, read git log + progress file, read feature list, start dev server via `init.sh`, run a basic end-to-end check (catches bugs left by previous sessions), then pick highest-priority unfinished feature — same URL
- Failure modes → fixes: one-shotting and running out of context → feature list + one feature/session; declaring victory early → full feature list up front; broken/undocumented state → progress notes + commits at end, smoke test at start; marking done without testing → browser-automation (Puppeteer MCP) end-to-end self-verification (unit tests/curl alone led to false "done"); no quantitative benchmark reported — same URL
- Later (Mar 2026): Sonnet 4.5 showed "context anxiety" (wrapping up early near perceived context limit) so context *resets* + handoff artifacts were essential; Opus 4.5 largely removed this, so resets were dropped for one continuous session with automatic compaction — https://www.anthropic.com/engineering/harness-design-long-running-apps

**Memory tool + context editing (Anthropic, Sep 29 2025) [VENDOR]**
- On an internal agentic-search eval: memory tool + context editing +39% over baseline; context editing alone +29%; in a 100-turn web-search eval context editing cut token consumption 84% and let agents finish workflows that otherwise died from context exhaustion. Context editing clears stale tool calls/results near limits; memory tool = client-side file directory Claude can CRUD across conversations — https://claude.com/blog/context-management

**Tool-definition bloat as a context cost (Anthropic "Advanced tool use", Nov 24 2025) [VENDOR]**
- Typical MCP tool-definition overhead: GitHub (35 tools) ~26K tokens, Slack (11) ~21K, Jira ~17K; five servers / 58 tools ~55K; Anthropic internal peak 134K before optimization — https://www.anthropic.com/engineering/advanced-tool-use
- Tool Search Tool (defer-loading tools): ~77K → ~8.7K tokens (−85%); MCP-eval accuracy Opus 4 49%→74%, Opus 4.5 79.5%→88.1% — same URL
- Programmatic Tool Calling (model writes code that calls tools, only results enter context): 43,588 → 27,297 tokens (−37%) on complex research tasks; internal knowledge retrieval 25.6%→28.5%; GIA 46.5%→51.2% — same URL
- Tool Use Examples in definitions: 72%→90% on complex parameter handling (internal) — same URL

### Inferences
- **CLAUDE.md / AGENTS.md sizing rule:** include only what the agent cannot infer and would otherwise get wrong (non-standard commands and tooling, repo-specific gotchas, hard constraints). Skip overviews and file-by-file descriptions. ETH found overviews in 95–100% of LLM-generated files, and they did not help. The one condition where generated files helped (+2.7%) was a repo with no docs at all, which suggests their value is as a *doc substitute*, not an add-on.
- Every instruction is followed, and following it costs steps (the `uv` and repo-tool usage jump). Conditional or rarely needed instructions belong in skills or linked docs loaded on demand, the "table of contents, not encyclopedia" pattern (OpenAI harness engineering; Claude Code skills). Must-happen rules belong in hooks.
- For tasks that span sessions, Anthropic's initializer/coding-agent split is directly reproducible in Claude Code and Cursor with no special infrastructure:
  - a `features.json` with pass flags the agent may only flip;
  - `progress.md`;
  - `init.sh`;
  - commit after each feature;
  - a startup routine of reading the log and git log, then running the smoke test.
- Context resets vs compaction is model-dependent. Resets with handoff files were needed for Sonnet 4.5's "context anxiety", while Opus 4.5+ ran continuously with compaction. Since a method should survive model changes, handoff files are worth keeping either way: they are cheap and they also serve humans.
- IDE checkpoints (Claude Code rewind) only capture edits made through the edit tools, not Bash changes, so git commits remain the real recovery mechanism.

### Gaps
- No public study measured CLAUDE.md length vs adherence for Claude Code specifically; IFScale uses keyword-inclusion in report writing, not coding instructions.
- ETH paper per-agent success numbers are only in figures; the "−3%" vs "−2%" AGENTbench figure is inconsistent within the paper.
- The Lulla et al. study does not name agents/models in the abstract and measures only efficiency.
- OpenAI's harness-engineering post could not be fetched (403); AGENTS.md "table of contents" details and throughput numbers are from secondary summaries.
- No quantitative evaluation of Anthropic's long-running harness (feature list / progress file) vs a baseline was published.

## 6. Model/tool selection (cheap/fast models for subagents, cost/latency trade-offs)

### Takeaway
A strong lead model that briefs well and delegates mechanical work to a cheaper or faster model now matches frontier quality at roughly 40–60% lower cost (Devin Fusion; Fable+sidekick −54% cost at the same score). On standardized scaffolds, small models trail flagships by only ~5–7 pp: Haiku 4.5 at 70.0% vs Opus 4.5 at 76.8% bash-only Verified; Haiku 4.5 at 73.3% vendor-reported. The savings depend on the lead's behavior: delegate early, write constraint-and-done-criteria briefs, review cheaply. Forced delegation, weak primaries, and judgment-heavy or serial-debugging tasks erase the gains. Per-token price is a poor predictor of agent cost. Turns, context size and cache hits dominate.

### Cited Findings
**Main-agent + cheap "sidekick" routing — Cognition Devin Fusion (Jun 29 2026; chart updated Aug 7 2026) [VENDOR]**
- Two agents in parallel, each with own toolset and cached context: a frontier main agent that takes "minimal actions" (plans, interprets ambiguity, delegates, monitors, final review) and a cheaper sidekick doing delegated execution; lightweight classifiers decide mid-task when to switch models; switches are timed at context compaction (a cache miss anyway) to avoid extra cache cost — https://cognition.com/blog/devin-fusion
- FrontierCode 1.1 Extended (score / avg cost per task): Fable 5 (xhigh) 64.9 / $10.53; Opus 5 (medium) 63.6 / $3.51; Devin Fusion 63.1 / $1.35; GPT-5.6 Sol (high) 58.7 / $3.41; Kimi K3 58.2 / $3.12; Grok 4.5 (high) 56.6 / $1.09. Claimed up to 60% cheaper than frontier models (revised from 35%); Fusion with Fable 5 41% cheaper than pure Fable 5 at same performance; 88% of internal merged PRs driven entirely by the Fusion router — same URL
- Per-task delegation examples: cost cuts of 25–62% on mechanical work (ES6 modernization −62%, OpenTracing removal −32%, JSON-Schema models −38%, UI team selector −28%, Quarkus MCP transport −25%); delegation works for mechanical/large refactors/removals/slow test runs and "backfires" on tasks where "the judgment is the deliverable" (per-task score columns on the page were garbled in extraction — not reported here) — same URL
- Earlier "smart friend" attempt with a *weak* primary (SWE-1.5) failed; cost savings only hold if both models are strong — https://cognition.com/blog/multi-agents-working

**How the lead delegates matters more than per-token price — Cognition "Making Fable Cheaper Than Opus" (Jul 13 2026) [VENDOR]**
- 3,000 eval sessions on FrontierCode 1.1 (deep analysis on 40 tasks); Fable 5 costs 2x Opus 4.8 per token, yet: pure Fable $4.03/run (score 60.8) vs pure Opus $3.06 (55.4); with a cheap sidekick: Fable $1.86 (60.7) vs Opus $2.04 (54.6) — Fable+sidekick 54% cheaper than pure Fable at nearly unchanged score — https://cognition.com/blog/making-fable-cheaper-than-opus
- Mechanism: Fable delegated *early* (first action often a handoff), wrote briefs listing constraints, edge cases and a definition of "done" and asked for a report before commit; Opus delegated late after doing the expensive work, dictated full file contents, and when reviewing pulled sidekick files back into context 2x more often with 4x more corrective edits. Lead stats: Fable 11.5 turns vs Opus 26.5; 6.1k vs 19.0k output tokens; 545k vs 1,679k cumulative lead input; lead never edited code in 81% of Fable-led runs vs 24% of Opus-led; ~3 handoffs/run for both. Example: same hashing task, Opus-brief result scored 25 vs Fable-brief 94 — same URL
- Lessons stated: per-token price is a poor predictor of agent cost (turn count, context size and what the lead chooses *not* to do dominate); forcing delegation alone hurt performance — it pays only when the lead trusts the sidekick; good briefs can *raise* quality; delegation has little value for short tasks or serial debugging "where the accumulated context is the work"; no latency data — same URL
- Fast retrieval subagents: SWE-grep-mini >2,800 tok/s and SWE-grep >650 tok/s vs Haiku 4.5 ~140 tok/s; same task completion in less wall time with Sonnet 4.5 main agent — https://cognition.com/blog/swe-grep

**Small-model subagents (Anthropic Haiku 4.5, Oct 15 2025) [VENDOR]**

- Built-ins: Explore (read-only, Write/Edit denied; thoroughness quick/medium/very thorough) and Plan (read-only, used in plan mode) both use the *main conversation's model* by default (Explore does not default to Haiku; override by defining an `Explore` subagent with `model: haiku`); general-purpose has all tools and uses `CLAUDE_CODE_SUBAGENT_MODEL` if set. ### Inferences
- A practical model policy for a Claude Code/Cursor method:
  - Main session on the strongest model for planning, ambiguity resolution, integration and final review.
  - Read-only exploration and log/test triage subagents on a fast or cheap model (Haiku-class), returning file:line pointers.
  - Mechanical, well-specified edits (renames, migrations, removals, test scaffolding) delegated to a cheaper model under a written brief with constraints, edge cases and a definition of done.
  - Judgment-heavy design, serial debugging and short tasks kept in the main thread.
  - Fresh-context review on a strong model.
- Delegation briefs are themselves a quality lever. In Cognition's data, Fable's brief yielded 94 vs 25 on the same task, and briefs that dictated whole files caused rework. A method should standardize a brief template: goal, constraints, edge cases, done-criteria, report format, and "report before commit".
- Switching models mid-session breaks the prompt cache. Devin Fusion times switches at compaction for this reason. In IDE terms, prefer delegating to subagents (separate caches) over flipping the main session's model mid-task, and use forks when the subtask needs the full parent context.
- Claude Code's built-in Explore subagent inherits the main model by default. Cheap exploration requires an explicit `model: haiku` override or `CLAUDE_CODE_SUBAGENT_MODEL`.

### Gaps
- No independent (non-vendor) benchmark of lead+sidekick routing for coding was found; Devin Fusion and FrontierCode are Cognition-internal.
- Haiku-class subagent *accuracy* for exploration (missed files vs main-model exploration) is unmeasured publicly; SWE-grep's F1 comparison is informal.
- Latency figures for Fusion/sidekick setups were not reported.
- Several 2026 models referenced by vendors (Fable 5, Opus 5, Opus 4.8, GPT-5.6 Sol, Mythos 5) appear only in vendor/aggregator tables; their official model cards were not checked.
